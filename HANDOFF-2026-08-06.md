### 2.3 Container tooling limits (these will bite you)

| Want | Problem | Use instead |
|---|---|---|
| `curl` on host | not installed | run from inside container |
| `sqlite3` in container | not installed | it IS on the host |
| DELETE/PATCH via `wget` | BusyBox wget has no `--method` | `docker exec n8n-n8n-1 node -e '...fetch...'` |
| `date -d '+2 hours'` in container | BusyBox date rejects it | compute on the host, pass via `-e` |
| `n8n execute --id=X` | task-broker port 5679 in use while running | wait for the real cron |
| n8n REST API | no `N8N_API_KEY` configured | CLI or wait for cron |

Working pattern for any Supabase data call:

### 2.4 ⚠️ WAL MODE — this nearly caused a destructive mistake

The n8n SQLite DB runs in **WAL mode**. `docker cp` of `database.sqlite` alone returns a
**stale** file. In this session that made a *successful* import look like it had failed.
Had that been trusted and re-deployed, working state would have been overwritten.

**Always copy all three files:**

```bash
rm -f /root/x.sqlite*
for f in database.sqlite database.sqlite-wal database.sqlite-shm; do
  docker cp n8n-n8n-1:/home/node/.n8n/$f /root/x.${f#database.}
done
sqlite3 -header -column /root/x.sqlite "SELECT ..."
```

### 2.5 Shell environment

Local shell is **Git Bash on Windows**.
- Heredocs work: `git commit -F - <<'EOF'`. PowerShell here-strings (`@'...'@`) do **not** —
  they produce `pathspec did not match` errors. (One commit, `b7a9854`, has a stray `@` in
  its subject from this. Cosmetic; left alone rather than rewriting shared history.)
- `tar`/`scp` need **Unix-style paths**: `/c/Users/...`, not `C:/Users/...`. `tar` reads
  `C:` as a remote host and fails with *"Cannot connect to C: resolve failed"*.
- In heredoc'd Python, `$SP` does **not** expand. `export SP=...` then read
  `os.environ['SP']`.

## 3. What was wrong (root cause)

Airtable returns *"The service is receiving too many requests from you"* with HTTP 429 —
which reads like a rate limit and caused an initial misdiagnosis. The actual error code is
**`PUBLIC_API_BILLING_LIMIT_EXCEEDED`**: the **monthly billing quota**. Retries, backoff
and stagger do nothing against it. It resets monthly, not hourly.

Evidence at diagnosis time: **432 errors vs 47 successes** over two days. Nine workflows
each failed exactly 47 times — all dying at their *first* Airtable node.

The decisive clue: **Morning Check-in was 47/47 green** while everything else was 0/47.
It was the one workflow already migrated off Airtable. Clean causal split.

### Blast radius — why Dwayne saw score 0

Dwayne (`client_da8719ab`) replied to his morning check-in every day. Every reply was lost:

- `biometrics` for him: **0 rows**
- `daily_scores` for him: **0 rows**
- `pending_replies`: Aug 2–6 all still `status=open`, `matched_reply=null`

The inbound router received each reply, tried to look him up in Airtable, got 429, and died
before parsing. No biometrics → nothing to score → 0 across all four pillars. **Not a
scoring bug.** The "you'll see your Executive Score" text he received is scheduled
onboarding copy that sends regardless of whether data exists.

Those 5 stale rows **cannot be retroactively matched** — that data is permanently lost.

**003 and 004 were authored in this session and are NOT part of the originally reviewed
spec** (`docs/superpowers/specs/2026-07-29-airtable-to-supabase-migration-design.md`),
which scoped those tables to later phases. They were required because the workflows cannot
run without them. Worth a review pass, particularly:

- `inbound_seen.message_sid` has a **`unique` constraint**. The search-then-create dedupe
  pattern is read-modify-write and **races** under webhook redelivery; the constraint is
  what actually guarantees once-only processing.
- `dead_letter` deliberately has **no FK** on `client_id`. It is the failure queue, and the
  failures most worth keeping are often those where `client_id` is wrong or missing — an FK
  would reject exactly those rows.
- `004` §4b **corrects 003**: `war_room_sessions` was modelled from the router's read-only
  use (one column), but the War Room's own upsert writes ten. Added as idempotent `ALTER`s
  rather than editing an already-applied migration.

### 4.2 Two design conventions the conversion depends on

1. **Identity lives in `profiles`; coaching fields live in `client_profile`.** They join via
   the `v_clients` view. `client_profile`'s PK is **`client_id`** — there is **no `id`
   column**. Duplicating identity across both tables is the split-brain the migration exists
   to remove.
2. **Updates key on natural business keys**, never Airtable's opaque `recXXX` ids:
   `pending_id`, `session_id`, `client_id`. Upstream code nodes were patched to carry these.

### 4.3 Views absorbing filters the n8n Supabase node cannot express

The node's filter UI only ANDs simple comparisons. Anything with `OR` or date arithmetic
moves into a view, and the node does a plain `getAll`:

| View | Replaces |
|---|---|
| `v_open_pending_replies` | `AND(status='open', OR(expires_at='', IS_AFTER(...)))` |
| `v_recent_morning_checkins` | `DATETIME_DIFF(NOW(),opened_at,'hours')<=26` |
| `v_open_war_room` | `committed_action=''` (NULL **or** empty) |
| `v_nudges_recent_18h` | `DATETIME_DIFF(NOW(),timestamp,'hours')<=18` |
| `v_daily_scores_last_7d` | `DATETIME_DIFF(NOW(),date,'days')<=7` |
| `v_clients_match` | War Room's phone-normalising `OR(...)` matcher |

**`v_clients_match` deserves attention.** The design doc predicted this filter would need a
Postgres node or RPC. It did not. The view explodes each client into every key they can be
recognised by — raw phone, **digits-only phone**, and GHL contact id — so the node filters
one column with a plain `eq`. Dwayne resolves to three rows:
`+19174637303`, `19174637303`, `FGRKMuONxezAC6d940BJ`.

The digits-only key removes the phone-format dependency that previously misidentified a
paying Pro client as non-Pro.

### 4.4 Converters

- `build/migration/convert_inbound_router.py` — the router's 9 nodes (bespoke)
- `build/migration/convert_workflows.py` — the other 12 workflows, 34 nodes (generalised)

Both **refuse to guess**. Any filter they cannot parse confidently is reported and the run

## 8. Ground rules

- **Never put the Supabase service key on a command line.** Read it from the container's env
  (`process.env.SUPABASE_SERVICE_KEY`) or a scratchpad file that is deleted after use. Redact
  values when grepping `.env` files: `sed -E 's/=.*/=<redacted>/'`.
- **These are live cron senders reaching real paying clients.** A bad deploy sends real SMS
  rather than merely erroring. Verify against `client_test` before anything touches the other
  ten, and snapshot before deploying.
- **Read WAL-inclusive** (2.4) before concluding anything about n8n DB state.
- Deploy sequence: `docker compose cp` into `/tmp` → `import:workflow` →
  `update:workflow --active=true` **per workflow** → `docker compose restart n8n`.
  `import:workflow` **deactivates** on import; the reactivation step is mandatory.
- **"Deregistered all crons" in the logs is shutdown teardown, not a failure.** It appears
  *before* the startup banner. What matters is the `Activated workflow "…"` lines after it.
- Cron schedules are **staggered across the hour** (`:05`, `:10`, `:15`, `:25`, `:30`, `:35`,
  `:40`, `:45`, `:50`). After a restart, expect several minutes of silence before the first
  execution — that silence is not evidence of breakage.
